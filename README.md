# مرصد الموارد الطبية — لوحة استجابة طبية جغرافية (GIS)

نظام مراقبة حيّ للموارد الطبية وسيارات الإسعاف عبر محافظات الجمهورية العربية السورية. صمّمتُ النظام ليمنح مدير القطاع الصحي صورة لحظية عن حالة المشافي والمستوصفات والنقاط الطبية الميدانية — نسب الإشغال، توزّع سيارات الإسعاف، والحالات الحرجة — مع القدرة على التدخّل واتخاذ قرارات توجيه يدوية.

المطوّر: **عبدالله زايد الجسار**

---

## المزايا الرئيسية

- **خريطة تفاعلية لسوريا**: توزّع المنشآت مع تجميع ذكي للعلامات (clustering)، وأشكال بصرية مختلفة حسب نوع المنشأة وحالتها.
- **مراقبة حيّة وتوجيه**: خوارزمية توزيع سيارات الإسعاف مبنية على استعلامات PostGIS المكانية، مع مؤشرات إشغال وتصنيف لوني (أخضر/أحمر).
- **فلترة**: حسب المحافظة ونوع المنشأة.
- **الآلة الزمنية**: استرجاع لقطات تاريخية لحالة الشبكة في أوقات سابقة.
- **تنبيهات وقرار يدوي**: إشعارات فورية عند الطوارئ، وواجهة تتيح للمدير توجيه سيارة إسعاف يدوياً إلى منشأة حرجة.
- **إدارة بيانات كاملة (CRUD)**: واجهة لإضافة وتعديل وحذف المنشآت وسيارات الإسعاف مباشرة.
- **تغذية بيانات حيّة**: محرّك محاكاة قائم على قواعد برمجية يولّد سيناريوهات طوارئ وحركة منطقية لسيارات الإسعاف لاختبار النظام.

---

## القرارات الهندسية (Architectural Decisions)

خلال التنفيذ واجهتُ تعارضاً جوهرياً في القيود التقنية المطلوبة، وأوثق هنا كيف عالجتُه لأن هذا القرار يمسّ صميم بنية النظام.

### التعارض: Serverless مقابل الاتصال الدائم

طُلب في المواصفة أمران لا يجتمعان مباشرة على منصة واحدة:

1. **واجهة خلفية على بيئة Serverless** (وظائف قصيرة العمر تُستدعى عند الطلب).
2. **اتصال دائم مستمر (Persistent Connection) عبر Socket.io** للبثّ الحي.

المشكلة أن وظائف الـ Serverless مصمّمة لتنفيذ قصير ثم تُطفأ، بينما الاتصال الدائم يتطلب عملية حيّة تبقى قيد التشغيل لتحمل الـ WebSocket المفتوح. لا يمكن لوظيفة serverless أن تحتفظ باتصال socket مفتوح لساعات.

### الحل: فصل المسؤوليات إلى خدمتين

قسّمتُ النظام إلى طبقتين، كلٌّ منهما على البيئة الأنسب لها:

| الخدمة | المسؤولية | البيئة |
|--------|-----------|--------|
| **الواجهة + مسارات API** (Next.js) | جلب البيانات (stateless)، الاستعلامات المكانية عند الطلب، الآلة الزمنية | Serverless — تُستدعى عند الطلب فقط |
| **السيرفر الحي** (Node/Express + Socket.io) | الاتصال الدائم، بثّ التحديثات، محرّك المحاكاة | عملية طويلة الأمد (Railway) |

بهذا الفصل:
- مسارات الـ API في Next.js تبقى عديمة الحالة (stateless) وتعمل بكفاءة على بيئة serverless — تُنفّذ استعلام PostGIS وتُعيد النتيجة وتُطفأ.
- السيرفر الحي المنفصل يحمل الاتصال الدائم ويبثّ التغييرات لحظياً لكل اللوحات المتصلة.

هذا الفصل ليس التفافاً على المتطلب، بل هو النمط المعماري الصحيح: كل قيد طُبّق على الطبقة القادرة على تحقيقه فعلياً، دون تضحية بأيٍّ منهما.

### إدارة حالة البثّ الحي

بدل الاعتماد على مكتبة بثّ جاهزة محدّدة، استخدمتُ **Zustand** كمصدر حالة مركزي وحيد (single source of truth) مع مستمع socket رفيع. هذا يمنحني نفس النتيجة (مزامنة الحالة الحيّة عبر الواجهة) بمكتبة مُصانة وموثوقة، مع تحكّم كامل بمنطق التحديث.

### كفاءة البثّ

النبضة الواحدة قد تغيّر حالة عشرات المنشآت دفعةً واحدة. لتفادي إغراق العملاء بعشرات رسائل socket منفصلة، بنيتُ **باثّاً مُقيّداً (throttled broadcaster)** يجمّع التحديثات ويبثّها دفعة واحدة كل ثانية على الأكثر، مع استثناء الأحداث العاجلة (التوجيه اليدوي، البلاغات) التي تُبثّ فوراً.

## عمق الاستعلامات الجغرافية (PostGIS)

بنيتُ المنطق الجغرافي على استعلامات PostGIS حقيقية، لا حسابات تقريبية في التطبيق:

- **أقرب سيارة إسعاف**: عامل `<->` (KNN) المدعوم بفهرس **GiST** لترشيح المرشحين بسرعة، ثم `ST_Distance` على النوع `geography` لمسافة دائرة عظمى دقيقة بالأمتار.
- **النطاق الجغرافي**: `ST_DWithin` لإيجاد كل السيارات ضمن مسافة محددة بكفاءة عبر الفهرس.
- **التجميع المكاني**: مؤشرات الإشغال والحالات الحرجة مجمّعة على مستوى المحافظة.
- **بؤرة الضغط**: `ST_Centroid` على تجميع المنشآت الحرجة لتحديد مركز ثقل الحاجة.

الاستعلامات المرجعية موثّقة في `database/spatial_queries.sql`.

## خوارزمية التوجيه

نُقلت من المخطط البياني المرفق حرفياً (`realtime-server/simulation/routing.js`):

```
احسب: الأسرّة المتاحة = الإجمالي - المشغولة
   │
الإشغال > 90% ؟
  نعم → الحالة: RED، إطلاق تنبيه → إيجاد أقرب إسعاف (ST_Distance) → توجيه
  لا  → الحالة: GREEN
```

عتبة الـ 90% ثابتة كما في المخطط، ومنطق التوجيه معزول في وحدة مستقلة لضمان مطابقته الدقيقة للمخطط دون خلطه بمنطق المحاكاة.

## تغذية البيانات ومحرّك المحاكاة

محرّك المحاكاة (`realtime-server/simulation/engine.js`) **سكريبت قائم على قواعد برمجية** — احتمالات ثابتة ومشي عشوائي محدود المدى، لا استدعاءات خارجية. يولّد:
- تغيّرات إشغال منطقية للمنشآت (مع انحياز خفيف يجعل بعضها يعبر العتبة الحرجة أحياناً).
- حركة سيارات الإسعاف نحو منشآتها المعيّنة خطوةً بخطوة.
- بلاغات طوارئ عشوائية بمعدّل محدّد.

هذا يوفّر تغذية حيّة واقعية لاختبار النظام، وقابلة لإعادة الإنتاج والتدقيق.

## التقنيات المستخدمة

- **الواجهة**: Next.js 14 (App Router) + TypeScript + React
- **الخريطة**: React-Leaflet + خرائط CARTO الداكنة (بلا مفتاح API)
- **إدارة الحالة**: Zustand
- **البثّ الحي**: Socket.io
- **قاعدة البيانات**: PostgreSQL + PostGIS
- **السيرفر الحي**: Node.js + Express

---

## التشغيل المحلي

### المتطلبات
- Node.js 18+
- PostgreSQL 14+ مع إضافة PostGIS

### 1) قاعدة البيانات

```bash
# أنشئ قاعدة بيانات ثم فعّل PostGIS ونفّذ المخطط والبيانات
psql -d gis_medical -f database/schema.sql
psql -d gis_medical -f database/seed.sql
```

### 2) السيرفر الحي

```bash
cd realtime-server
cp .env.example .env      # ضع DATABASE_URL الخاص بك
npm install
npm start                 # يعمل على المنفذ 4000
```

### 3) الواجهة

```bash
cd frontend
cp .env.example .env      # ضع DATABASE_URL و NEXT_PUBLIC_REALTIME_SERVER_URL
npm install
npm run dev               # يعمل على المنفذ 3000
```

ثم افتح `http://localhost:3000`.

> **مهم**: المتغيّر `NEXT_PUBLIC_REALTIME_SERVER_URL` يجب أن يحمل بادئة `NEXT_PUBLIC_` كي يصل إلى المتصفح، لأن المتصفح يفتح اتصال Socket.io مباشرةً إلى السيرفر الحي.
